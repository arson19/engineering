KUBERNETES · DEPLOYMENT ENGINEERING

From Kubernetes YAML to Helm Charts

How to move from copy-pasted manifests to reusable, configurable deployment packages — without losing control of what reaches a cluster.

Kubernetes manifests describe the desired state of an application. A Deployment defines pods and rollout behaviour, a Service provides stable networking, and ConfigMaps hold non-sensitive configuration. For a small application, a few YAML files are easy to manage.

The challenge appears when the same application must run in multiple environments or for multiple customers. Small differences accumulate: image tags, replica counts, resource limits, hostnames, feature flags and environment-specific settings. Copying entire manifests for every variation creates drift and makes upgrades harder to reason about.

Why raw manifests become difficult to maintain

  • Duplication: the same Deployment is repeated with only a few values changed.
  • Configuration drift: a security or reliability fix is applied to one copy but missed in another.
  • Review overhead: reviewers must distinguish meaningful changes from environment-specific noise.
  • Release complexity: coordinating a consistent application version across environments becomes harder.
The goal is not to template every field. The goal is to identify the small set of values that legitimately varies, while keeping safe defaults and operational behaviour consistent.

What Helm adds

Helm packages Kubernetes resources into a chart. Templates describe the resources, while a values file supplies configuration for a particular installation. A chart can be versioned, reviewed and installed repeatedly.

Chart templates+values.yaml→Rendered manifests→Kubernetes

A minimal chart structure

sample-service/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    └── service.yaml

Chart.yaml describes the chart. values.yaml contains defaults. Files under templates/ are rendered using those values.

Define sensible defaults

replicaCount: 2

image:
  repository: nginx
  tag: "1.27"
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi

These values are examples for a small demonstration service. Production values should be chosen from measured application requirements and cluster capacity.

Template the Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}
    spec:
      containers:
        - name: app
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - containerPort: 80
          resources:
            {{- toYaml .Values.resources | nindent 12 }}

Make environment differences explicit

Keep common defaults in values.yaml and add small override files for environments. For example, a development override might use one replica, while a production override might increase replicas and set stricter resource requests. Avoid copying the full chart for each environment.

# values-prod.yaml
replicaCount: 3

image:
  tag: "1.27.1"

resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 1
    memory: 1Gi

Validate before applying

Helm makes rendering repeatable, but it does not remove the need for validation. A practical workflow includes:

  1. Lint the chart with helm lint ./sample-service.
  2. Render manifests with helm template demo ./sample-service -f values-prod.yaml.
  3. Review the rendered resources and run policy or schema checks used by your team.
  4. Deploy to a non-production namespace and verify readiness, service routing and application behaviour.
  5. Promote the same chart version with environment-specific values.

Operational considerations

  • Use readiness and liveness probes that reflect the application's actual health.
  • Set resource requests and limits based on observed usage, not arbitrary copy-paste values.
  • Keep secrets out of chart values committed to source control. Reference an approved secret-management mechanism instead.
  • Use immutable image tags or digests for reproducible releases.
  • Document chart inputs and supported Kubernetes versions.
  • Plan chart upgrades and rollbacks; a successful Helm command alone does not prove application health.

When Helm is not the answer

For a tiny application deployed once, plain manifests may be simpler. Helm becomes useful when packaging, repeatable installation, versioning and controlled configuration are real requirements. Kustomize is another option when environment overlays are the primary need.

Takeaway

Moving from raw YAML to Helm is less about introducing another tool and more about creating a reliable deployment contract. Keep templates small, make configuration intentional, validate rendered output and treat chart versions as release artifacts.

Try it yourself: create a chart for a small HTTP service, add development and production values, render both, and compare the output. Keep the example independent of any employer or customer environment.
